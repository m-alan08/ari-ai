# Pilot metrics — feedback loop, budget visibility, customer health

## Feedback loop (what we measure weekly, per customer)

| Metric | Definition | Source (verified) | Baseline we already hold |
|---|---|---|---|
| Onboarding success | % of invited customers reaching a completed first assessment unaided after step 5 | checklist + assessment records | — |
| Genuine findings | validated findings per repo/week | findings API (`Finding` records) | eval: IDOR 8/8 validated |
| False positives | findings disputed/accepted-risk vs. total flagged | `AcceptRisk` records + support log | eval benign FP: 0/8 in baseline |
| Actionable fixes | fix PRs merged by customer / fix PRs opened | GitHub PR state + findings patches | eval: 8/8 IDOR fixed |
| Verified regressions | regenerated tests that catch the defect pre-fix and pass post-fix | Verify evidence artifacts | exists per patched case |
| Runtime | assessment duration p50/p95 | assessment `usage` + timestamps | median 153 s (45-case) |
| Dollars | `usage.usd` summed per project/week; flag > $50/day global cap approach | `assessments.doc.usage` | ~$0.03/run; $1.26 baseline total |
| Support burden | tickets per customer/week + owner minutes | support log | — |

Weekly cadence: owner exports the per-customer health report below, reviews
with the team, feeds disputes/disagreements back as eval cases
(`security-agents/evals/commits/cases.json` is the yardstick harness).

## Quota and budget visibility (truthful)

What exists **today**:

- Hard caps enforced in worker/settings (PILOT_SCOPE.md quota table).
- Per-assessment `usage` (tokens, USD, sandbox seconds, calls) persisted on
  the assessment doc — inspectable via `GET /assessments/{id}`.
- Customer-facing settings show their monitoring budget fields.

What does **not** exist: a customer-facing usage dashboard, per-customer
metering for billing, or any paid plan. Do not present pricing tiers as
functional — the pricing page itself says so ("nothing can be purchased").

Pilot stop-loss rule: if any customer's observed weekly spend exceeds
**$25**, owner reviews before continuing — well under the $50/day global
ceiling, caught by the weekly report.

## Per-customer health report (the pilot "admin dashboard")

We deliberately ship a **report**, not a new dashboard: a new admin UI would
be exactly the place a cross-tenant bug hides. The report is assembled from
existing membership-gated endpoints, so it can only ever contain the one
organization it was generated for.

Per customer, weekly, generated by the owner (script over the API with an
owner session; ~30 lines — see FIRST_FIVE_PLAN.md tooling note):

| Section | Source endpoint (all require project membership) |
|---|---|
| Assessments: count, completed/failed/cancelled, p50 duration, USD | `GET /projects/{id}/assessments`, `GET /assessments/{id}` |
| Findings: new, validated, inconclusive, disputed | `GET /projects/{id}/findings` |
| Monitoring: events, deferrals, blocked commits | `GET /projects/{id}/events`, reassessments list |
| Defense Lab: ingest windows, shadow decisions, incidents, health | `GET /projects/{id}/pilot-report`, `/defense-health` |
| Approvals pending / stale | `GET /projects/{id}/approvals` |
| Audit anomalies (scope revocations, failed auths) | `GET /audit` (owner-only) |

The owner-facing roll-up across the five customers lives only in the ops
report (spreadsheet/doc), never in the product — the product shows each
customer only their own org.
