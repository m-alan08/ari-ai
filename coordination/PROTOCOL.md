# Multi-agent coordination protocol

How every coding agent on `ari-ai` stays in sync **without a human relay**. GitHub is the
source of truth; everything here survives session restarts.

## Where things live

| What | Where | Who writes it |
|---|---|---|
| Live agent-to-agent messages | [Issue #559 — AGENT COMMS](https://github.com/adamissac/ari-ai/issues/559) comments | any agent, one comment per message, never edit others' |
| Shared dashboard (rendered view) | `coordination/AGENT_BOARD.md` | regenerated by `scripts/coordination_board.py`, never hand-edited |
| Your durable state | `coordination/status/agents/<agent>.json` | you only — one file per agent, no write contention |
| Long-lived per-owner status | `coordination/status/<PERSON>.md` | that owner |
| Immutable messages / decisions | `coordination/messages/<UTC-ts>-<from>-to-<to>-<slug>.md` | sender, append-only |
| Handoff log | `docs/planning/SESSION_HANDOFF.md` | newest entry at top |
| Ownership lanes | `coordination/OWNERSHIP.md` | reviewed changes only |

## States

```
CLAIMED → WORKING → READY_FOR_REVIEW → MERGED → DONE
                ↘ NEEDS_COORDINATION ↗   (overlap suspected)
                ↘ BLOCKED              ↗   (waiting on another agent or a human)
```

## Onboarding — what a new (or restarted) agent does

1. `git fetch origin --prune`; read `coordination/AGENT_BOARD.md`.
2. Read issue #559's recent comments for un-acked requests naming you.
3. Read your `coordination/status/agents/<you>.json` — that is your durable handoff:
   task, branch, latest SHA, tests run, blockers, next action.
4. `gh pr list --state open` + `git for-each-ref refs/remotes` to see branches that moved.
5. Post `[CLAIMED] <you> → all: <task> (paths: …)` on issue #559 **before** editing files
   another agent might also touch; update your JSON `state`, `claims`, `next_action`.

## Claiming and overlapping work

- `claims` in your JSON records the paths/subsystems you are changing. If another agent's
  `claims` overlap yours, post `NEEDS_COORDINATION` on #559 naming the files, and agree a
  division (different files / order / owner keeps it) **before** pushing.
- Ownership lanes in `OWNERSHIP.md` still govern *writes*; claims are for currently active
  work. If the two disagree, the lane owner wins unless they delegate on #559.

## Integration gate (for the release/integration agent)

Before **every** merge, re-check:

1. `coordination/AGENT_BOARD.md` blockers/claims,
2. #559 comments newer than your last check (new CLAIMED entries can appear mid-run),
3. the PR's own checks.

If a PR overlaps a lane held for another agent or a `BLOCKED`/`NEEDS_COORDINATION` claim,
hold the merge and post on #559 instead of guessing.

## Updating the board

```bash
# edit only your own record
$EDITOR coordination/status/agents/<you>.json
python3 scripts/coordination_board.py          # rewrites coordination/AGENT_BOARD.md
git add coordination/status/agents/<you>.json coordination/AGENT_BOARD.md
git commit -m 'coord(<you>): <state> — <one-line update>'
```

A scheduled/manual workflow (`.github/workflows/coordination-board.yml`) re-renders and
commits the board when records drift, so agents never fight over the same file.

## What NOT to do

- Don't use one shared Markdown file as a chat log (that's why #559 exists).
- Don't edit another agent's JSON or the generated board by hand.
- Don't treat a posted message as acknowledged — wait for a reply for anything blocking.
- Don't create coordination infrastructure outside GitHub/this repo.
- Don't bypass PR reviews, branch protection, or security sign-offs.
